# 游戏客户端接入

需要直接复制到游戏项目的完整协议、字段约束、错误码、重试策略和 Lua 示例，见 [FQ 游戏服务器接口技术说明](FQ游戏服务器接口技术说明.md)。

## 创建凭据

玩法分析的开关、上报字段、重试和统计口径见 [可选玩法分析接入](#可选玩法分析接入)。

管理员或持有“管理游戏 API Key”权限的用户进入地图工作区“客户端接入”，为地图创建具有最小权限的 Key。同一地图可以创建多把 Key 以便拆分权限和轮换，所有 Key 共享该地图运行数据。新 Key 的 Token 由后端同时保存 SHA-256 认证哈希和 AES-256-GCM 密文，可随时从详情查看或点击 Token 旁的复制控件复制；列表仍只显示前缀，每次查看都会写入审计。

请求统一携带：

```http
FQ-Map-Key: fqmap_生成的完整Token
Content-Type: application/json
```

所有游戏端专属接口统一使用 `/api/fq` 前缀。Key 已绑定地图，客户端请求体不要自行传 `mapId`。

## 存档读取与保存

开局优先调用 `POST /api/fq/bootstrap`，一次读取本局涉及的玩家和地图全局存档：

```json
{
  "uids": ["player-001", "player-002"],
  "includeGlobal": true
}
```

返回的每份存档都有 `revision`。尚未保存过时返回 `revision: 0` 和空对象；被后台标记为“存档封禁”的玩家返回 `dataBanned: true`，不下发已有存档。

保存时提交完整存档对象，而不是数据库字段名或 SQL：

```http
POST /api/fq/archives/players/player-001/save
```

```json
{
  "requestId": "FQ-game-20260716-000001",
  "expectedRevision": 0,
  "values": {
    "gold": 100,
    "inventory": ["sword"],
    "progress": { "chapter": 2 }
  }
}
```

- `requestId` 必须以 `FQ-` 开头。同一次网络重试必须复用同一个 `requestId` 和完全相同的内容。
- `expectedRevision` 必须等于最近一次读取到的版本。保存成功后版本加一；版本不一致返回 `409 FQ_ARCHIVE_REVISION_CONFLICT`。
- 该存档没有发生后续更新前，相同 `requestId` 重放会返回相同的新 revision；同一 ID 改写内容返回 `409 FQ_REQUEST_REUSED`。更旧的迟到重试会被 revision 冲突安全拒绝。
- 玩家和全局存档单份上限为 512 KiB。JSON 整数如果可能超过 JavaScript 安全整数范围，应改用字符串。
- 游戏只能通过 FQ API 读写，不连接 PostgreSQL，也不在客户端保存数据库账号。

## 消息领取与礼包资格

消息和礼包先通过 `POST /api/fq/deliveries/query` 批量读取最多 24 个 UID，响应仍按请求 UID 归位。只消费礼包的地图应提交 `includeMessages: false`，此时只需 `game.gifts.read`，后台不查询也不返回消息。启用消息时额外需要 `game.messages.read`；消息采用“游戏内写入成功 → ACK”的顺序，未确认记录会再次返回，客户端必须按消息 ID 幂等。

礼包资格不按 UID 判断：后台使用玩家资料上报中的完整昵称（如 `酒徒#8023`）精确匹配，同名多 UID 的同一礼包取最大正数值。礼包只返回 `{ gift_key, value }` 当前快照；客户端只把 `value > 0` 的项写入本局资格缓存，不写玩家存档、不累计、也不 ACK。每次新开局重新查询，后台设为 `0` 后下一局即取消。《沧澜》的 `gift_key` 必须与现役福利礼包名称完全一致，未知 Key 会被忽略。

消息 ACK 示例：

```json
{ "uid": "player-uid" }
```

自动指标事件统一请求：

```json
{
  "sessionId": "平台开局时间-房间完整标识",
  "uids": ["player-001", "player-002"]
}
```

游戏确认正式开局时调用 `sessions/start`，此后每 60 秒向 `sessions/heartbeat` 上报仍在线 UID，结算时停止心跳并调用 `sessions/end`。UID 会去重且最多 24 个；同一会话的开始、心跳和结束都可安全重放，重复开始/结束固定使用首次事件时间，结束后的迟到心跳不再写活跃事实。地图只取 Key 绑定值，日期与时间只取服务端 `Asia/Shanghai` 时间，客户端不得上传统计日期。

后台从首条自动会话起计算累计用户、在线用户、游戏有效局、日新增、日活跃、30 日流失、流失后回流、活跃次留、新增次留、七日留存和当日进入至少 4 局的复玩率。游戏有效局按北京时间开局日归属，只有首次结束或最后心跳与首次开局的服务端观测跨度严格超过 10 分钟才计入，正好 10 分钟不计；同一 `sessionId` 仍只计一局。比率保留两位小数并同时返回分子、分母，无样本时后台界面显示为暂无数据。自动会话存在后不再读取旧按日快照，旧 `POST /api/fq/metrics` 只为尚未迁移的地图保留，且不能推算游戏有效局。

## 排行榜上报

后台先在当前地图创建排行榜，并取得创建后不可修改的稳定榜单 Key。`latest` 每日首份覆盖，`best` 每日首份仅更优；`realtime_latest` 每次上报覆盖，`realtime_best` 每次上报仅在严格更优时更新。每日限制按 FQ 服务器北京时间自然日计算，独立采集记录不会因后台移除候选而丢失；实时策略也保存采集事实，切回每日策略后当天不会重新采集。候选池不会直接下发游戏，只有后台人工点击“发布前 100 名”后，新开对局才读取最新快照。

读取最新发布前 100 名、快照内当前房间玩家名次和今日采集状态：

```http
POST /api/fq/leaderboards/game_power/query
```

```json
{
  "uids": ["player-001", "player-002"],
  "limit": 100
}
```

响应中的 `published` 表示是否已经人工发布；没有快照时 `entries/playerRanks` 为空且不会回退实时榜。`submittedTodayUids` 在每日策略下用于跳过当日已采集玩家，实时策略下固定为空数组，`publishedAtText` 是游戏应展示的榜单更新时间。榜外玩家不返回本人名次。

```http
POST /api/fq/leaderboards/game_power/entries
```

```json
{
  "entries": [
    {
      "uid": "player-001",
      "name": "玩家名称",
      "gameLevel": "N2",
      "score": 9900,
      "gameCount": 18,
      "metadata": { "season": 3 }
    }
  ]
}
```

成功响应只确认请求已经完成；结果不确定时可安全重试，同日重复请求会被原子跳过，不会二次更新成绩。

## 风险事件上报

后台先创建并启用规则。`eventId` 是客户端生成的幂等键：网络重试必须继续使用同一个值，服务端不会重复创建事件。`details` 只能放处置所需的结构化证据，禁止上传账号口令、完整 Token 或其它无关敏感信息。

```http
POST /api/fq/risk/events
```

```json
{
  "eventId": "server-01-20260714-000001",
  "ruleKey": "abnormal_power_growth",
  "uid": "player-001",
  "playerName": "玩家名称",
  "count": 3,
  "details": { "delta": 8800 },
  "occurredAt": "2026-07-14T20:30:00+08:00"
}
```

API 成功返回 `{ "success": true }` 或 `{ "success": true, "data": ... }`；失败时使用 `{ "success": false, "error": { "code", "message" }, "requestId" }`。客户端日志应记录 `requestId`，但不得记录完整 API Key。

## 《沧澜》现有框架如何读取

当前《沧澜》已完成 FQ 适配层实现，不再连接旧 `/war3/...` 接口。服务器框架入口位于 `scripts/maps/server/init.lua`，由 `scripts/maps/init.lua` 用“风起服务器加载完毕 / 加载失败”门闩控制游戏模块启动；核心实现位于 `FQHttpClient.lua` 与 `FQServer.lua`。

`FQHttpClient` 固定请求 `https://fengqigame.com/api/fq/**`，并统一传入：

```lua
headers = {
    ['FQ-Map-Key'] = FQ_API_KEY,
}
```

当前开局顺序：

1. 先沿用现有平台逻辑取得本局玩家 UID。
2. 由一个本地客户端调用 `POST /api/fq/bootstrap`，`uids` 传本局全部玩家 UID。
3. 一次批量 upsert 全房玩家资料。
4. 读取最新发布榜单并一次批量读取全房消息/礼包；成功且无待投递时，四人房开局共 4 个 HTTP。
5. `JSON.decode(resp.body)` 后判断 `result.success == true`；投递仍先落入玩家完整存档，保存成功后才 ACK。
6. 英雄落地后只批量提交 `submittedTodayUids` 之外的玩家；全部已采集时不发送排行榜写请求。

当前实现已经选择原始 JSON：`ServerPlayerData` 保留字符串、数字、布尔与表，不再对 FQ 值执行旧 Base64 解码。玩家和全局完整快照分别维护 revision，保存重试复用完全相同的 requestId、expectedRevision 与请求正文。

在当前原始 JSON 实现下，数据库表名、数据库密码和 SQL 都不会出现在游戏代码中。数据库维护由后台和运维脚本负责，地图只认识 FQ API、UID、JSON 存档、revision 与 requestId。

代码实现不等于真实环境已经验收；完整交接状态、权限与实机顺序见 [沧澜项目 AI 技术交接](沧澜项目AI技术交接.md)。

## 可选玩法分析接入

管理员在“项目配置 → 开放功能”中按地图开启；新模块默认关闭，原有功能保持当前状态。关闭后隐藏数据页，查询与上报返回 `403 FEATURE_DISABLED`，历史保留。后台需要当前地图 `metrics.view`，上报需要绑定地图的 API Key 与 `game.metrics.write`。

| feature | 功能 | 统计对象 |
| --- | --- | --- |
| difficulty | 难度通关率 | 地图实际使用的难度编号 |
| choices | 选项选择统计 | 地图定义的技能、装备、路线等候选 |
| stages | 阶段退出统计 | 地图定义的教学、成长或流程阶段 |

没有关卡表现、挑战表现或技能通关率模块。迁移 `007_difficulty_analytics.sql` 移除旧关卡/挑战开关并增加配置版本，历史记录保留；不能把旧的团队关卡/挑战次数当作玩家难度选择次数。难度通关率需要独立开启和接入。

### 难度选择与通关

`POST /api/fq/analytics/events`，一份请求一条事件，正文禁止传 `mapId` 或未知字段。玩家确定本局难度时发送：

```json
{
  "type": "difficulty_select",
  "feature": "difficulty",
  "eventId": "game-001-player-a-select",
  "playId": "game-001",
  "uid": "player-a",
  "difficulty": 1,
  "version": "1.0.0"
}
```

确认选择事件成功后，该玩家本局通关时发送：

```json
{
  "type": "difficulty_clear",
  "feature": "difficulty",
  "eventId": "game-001-player-a-clear",
  "playId": "game-001",
  "uid": "player-a"
}
```

- `playId` 为地图内唯一的对局 ID，新开一局必须使用新 ID；同一局中每位玩家分别上报，每个 `playId + uid` 只能确定一次难度和通关一次。不要在预览难度、点击切换时重复上报，只报本局最终选定值。
- `difficulty` 为 1～1000 的整数，页面显示“难度 N”，按数值排序；不限制地图只能有 10 个难度。没有难度玩法的地图无需开启。
- `version` 必填，最长 64 字符。通关使用原 `playId + uid` 关联选择的难度与版本，不重复传入这些字段；未找到选择或已通关返回 `409 DIFFICULTY_NOT_OPEN`。新事件 ID 重复选择返回 `409 DIFFICULTY_CONFLICT`。
- 只上报实际通关的玩家；失败、退出或未完成不会增加通关次数。后台不从团队胜利推断所有玩家个人通关。

### 选项选择

一次已经完成或主动放弃的选择：

```json
{
  "type": "choice",
  "feature": "choices",
  "eventId": "game-001-player-a-choice-1",
  "choiceId": "game-001-player-a-choice-1",
  "uid": "player-a",
  "objectKey": "equipment-choice",
  "objectName": "装备选择",
  "version": "1.0.0",
  "position": 1,
  "candidates": [{ "key": "shield", "name": "护盾" }, { "key": "boots", "name": "靴子" }],
  "selectedKey": "shield"
}
```

- `choiceId` 在地图内唯一；每位玩家每次新选择用新 ID。`position` 表示第几次选择，范围 1～1000，不是候选在屏幕中的位置。
- 候选为 1～100 个唯一 Key，`selectedKey` 必须属于候选；明确放弃传 `null`。未完成且未上报的选择不进入出现次数。刷新候选应作为另一次选择，旧轮次明确放弃后传 `null`。
- `difficulty` 可选，为最长 64 字符的地图自定义字符串。对象/候选名称最长 160 字符；相同 Key 应保持同一含义，规则变化用新 Key 或新版本。

### 阶段进入与结束

```json
{
  "type": "start",
  "feature": "stages",
  "eventId": "game-001-tutorial-start",
  "runId": "game-001-tutorial",
  "objectKey": "tutorial",
  "objectName": "教学阶段",
  "version": "1.0.0",
  "uids": ["player-a", "player-b"]
}
```

确认进入事件成功后，结束同一阶段：

```json
{
  "type": "end",
  "feature": "stages",
  "eventId": "game-001-tutorial-end",
  "runId": "game-001-tutorial",
  "outcome": "success",
  "durationSeconds": 300
}
```

- `runId` 在同地图内唯一，每次进入阶段使用新 ID。`uids` 为 1～24 个不重复 UID；共同结算的多人阶段只报一份，进入次数计 1 次。各玩家结果不同时需分别建立记录。
- `outcome` 为 `success/failure/exit`，分别表示完成、失败、主动退出；没有结束事件显示未结束，不从断线推断退出。
- `durationSeconds` 必填，范围 0～604800 秒，为地图观测的实际游戏时长。可选 `reason` 最长 160 字符；start 可选字符串 `difficulty` 最长 64 字符。
- 正常进入下一阶段报 success，明确放弃报 exit；该功能统计各阶段的退出，不表示严格顺序漏斗，也不推断流失因果关系。

### 重试、关闭与清理

所有 ID、UID、对象/候选 Key 最长 128 字符。成功只返回 `{ "success": true }`。重试保持原 `eventId` 与完整正文（包括数组顺序），相同事件不重复计数；同一事件 ID 改写内容返回 `409 EVENT_CONFLICT`。新事件 ID 重复进入阶段或重复选择返回 `RUN_CONFLICT/CHOICE_CONFLICT`，结束事件未找到尚未结束的阶段返回 `RUN_NOT_OPEN`，均不产生部分写入。

关闭期间不接收事件，收到 `FEATURE_DISABLED` 后停止该模块采集，不积压后回填成重开日数据。重新开启后历史保留，原选择/进入记录仍可配对通关/结束。运行清理删除当前地图的分析与幂等记录，保留开关。

### 查询与计算

`GET /api/maps/:mapId/analytics/:feature?date=YYYY-MM-DD`，日期按服务端北京时间自然日。`version` 可选，按原值精确匹配；choices/stages 还支持字符串 `difficulty` 筛选。难度通关率始终按各难度编号分别汇总，未指定版本时合并版本并按 UID 去重。

| 难度通关率字段 | 定义 |
| --- | --- |
| 选择人数 selected_users | 当天选择该难度的去重 UID 数 |
| 通关人数 cleared_users | 上述选择记录中已通关的去重 UID 数 |
| 人数通关率 | 通关人数 ÷ 选择人数 |
| 选择次数 selected_count | 当天选择该难度的玩家对局记录数 |
| 通关次数 cleared_count | 上述选择记录中已通关的记录数 |
| 次数通关率 | 通关次数 ÷ 选择次数 |

同一玩家当天同一难度玩三局、通关一局：选择人数 1、通关人数 1、选择次数 3、通关次数 1。多人局按每位玩家分别计次；相同请求重试不计新次数。统计归属首次选择被服务端接收的日期，跨日通关更新选择日，后续结果可能改变历史日通关率。未通关记录仍在选择分母中。无记录时显示暂无数据，不伪造 0%。页面提供两组对比图与七列明细。

选项按接收日、场景 Key、position、候选 Key 汇总，被选率 = 选择次数 ÷ 候选出现次数，人数各自按 UID 去重。阶段按进入日和对象 Key 汇总，人数按 UID 去重，进入次数按 runId 计；完成率/退出率的分母是全部进入次数（含未结束），完成耗时是已完成样本中位数。跨日结束归原进入日。

所有计数只覆盖实际接入数据，不从旧埋点累计数回填。结果由地图权威逻辑生成，后台不代替游戏规则判定。

管理员开关接口：`PUT /api/maps/:mapId/analytics-features`，正文如 `{ "features": ["difficulty"], "revision": 0 }`。地图详情返回 `analyticsFeatures/analyticsRevision`；过期版本返回 `409 FEATURES_CONFLICT`。保存与审计同事务，关闭与上报通过地图行锁串行确定先后。
