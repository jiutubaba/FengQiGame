# 协作开发与交接

适用于 `jiutubaba/FengQiGame` 的维护者。仓库管理员、开发者、发布人分别使用自己的身份；Git 写权限不代表正式服务器权限。

## 1. 交给第二位维护者的资料

可以直接发送以下内容：

```text
项目：风起游戏管理后台
Git HTTPS 地址：https://github.com/jiutubaba/FengQiGame.git
接入手册：https://github.com/jiutubaba/FengQiGame/blob/main/docs/协作开发与交接.md
请先提供你的 GitHub 用户名，接受协作者邀请，再用自己的 GitHub 账号登录。
安装 Git、GitHub CLI、Node.js 24、PowerShell 7，以及本机 PostgreSQL 17。
各自使用自己的 Codex 账号；打开克隆目录后，让 AI 先读 AGENTS.md 和本手册。
第一个任务：建立本地环境，提交一个小范围 PR，完成另一位维护者审核和 CI。
正式发布权限单独授权；开发不需要原维护者的密钥或生产数据库。
```

| 资料或权限 | 交付方式 |
| --- | --- |
| 仓库地址、本文、任务编号 | 普通消息发送；当前仓库公开 |
| Git 写权限 | 管理员邀请对方自己的 GitHub 用户名，对方接受 |
| GitHub SSH 密钥 | 可选；对方在自己电脑生成，将公钥登记到自己的 GitHub 账号 |
| 阿里云发布权限 | 管理员分配独立 RAM 身份，对方在自己电脑完成 OAuth 登录 |
| 初次 RAM 登录信息 | 使用组织的安全凭据交付渠道，要求首次修改密码并绑定 MFA；不放入 Issue、PR 或 AI 聊天 |
| 本地 `.env` | 对方运行首次配置自行生成 |
| 生产 `.env`、私钥、OAuth 配置、GitHub Token、玩家数据、备份 | 不作为开发交接附件，不复制到对方开发目录 |

### 管理员邀请

打开仓库 Settings → Collaborators → Add people，按对方确认的 GitHub 用户名邀请。对方接受后，核对成员列表和写权限。不要以另一个姓名相近的账号代替，也不要默认授予仓库管理或云管理权限。

当前仓库属于个人账号。转入 Organization、改为私有仓库、增购套餐属于后续独立决策；变更前核对保护规则、Actions、发布制品下载和成员权限。

## 2. 对方首次安装与登录（Windows）

安装 Git、GitHub CLI、Node.js 24、PowerShell 7、PostgreSQL 17。PostgreSQL 选择仅用于本机开发的实例，记录实际端口；下面以 `5432` 为例。需要容器验收时再安装 Docker Desktop，CI 使用独立 PostgreSQL 17 服务。

在 PowerShell 中检查版本：

```powershell
git --version
gh --version
node --version
npm --version
$PSVersionTable.PSVersion
```

使用自己的 GitHub 身份登录。浏览器显示的设备验证码只由本人输入官方登录页面：

```powershell
gh auth login --hostname github.com --git-protocol https --web
gh auth setup-git
gh api user --jq .login
git clone https://github.com/jiutubaba/FengQiGame.git
```

用终端打开新建的 `FengQiGame` 目录；以下命令均在仓库根目录执行：

```powershell
git config user.name "你的提交署名"
git config user.email "你在 GitHub 验证过的邮箱或 noreply 邮箱"
git config pull.ff only
git remote -v
npm ci
npm run check
npm run audit:prod
```

如果只读克隆成功但推送失败，先核对 `gh api user` 和邀请接受状态；不要索要原维护者的 Token。Git 提交署名不会授予仓库权限。[GitHub CLI 登录说明](https://cli.github.com/manual/gh_auth_login)

### 可选：使用 SSH

HTTPS 浏览器登录已经满足协作，无需再设置 SSH。坚持使用 SSH 时，在 GitHub 官方设置流程中生成个人密钥并登记 `.pub` 公钥；私钥始终留在生成它的电脑。SSH 仓库地址为 `git@github.com:jiutubaba/FengQiGame.git`，首次连接先核对 GitHub 官方主机指纹。生产服务器 SSH 是另一套权限，不能用 GitHub 公钥登记代替服务器授权。[GitHub SSH 指南](https://docs.github.com/en/authentication/connecting-to-github-with-ssh)

## 3. 本地数据库与开发启动

推荐先使用既有原生模式完成热更新开发。确认本机 PostgreSQL 已启动，并且没有从旧终端继承生产 `DATABASE_URL`。不要读取、复制原维护者的 `.env`。

首次在仓库根目录执行（端口按自己的 PostgreSQL 实际配置替换）：

```powershell
.\首次配置.ps1 -Mode native -PostgresPort 5432
```

按提示填写本地管理员、本地数据库管理员密码和站点地址 `http://127.0.0.1:3000`。脚本创建本地业务数据库、迁移和初始账号，并生成 Git 忽略的 `.env`；已有 `.env` 时不会覆盖。数据库管理员密码不写入 `.env`。本地管理员建议使用至少 12 位独立密码；当前脚本最低校验为 6 位。

如果以前用 `启动网站.bat` 启动过原生服务，先用下列命令停止受项目管理的进程，再启动开发模式。陌生进程占用 3000 时先核对归属，不直接杀进程：

```powershell
.\运维\启动本机服务.ps1 -StopOnly
$env:NODE_ENV = 'development'
npm run dev
```

首次没有后台进程时可直接执行最后两条。按终端输出打开 Vite 地址（默认 `http://127.0.0.1:5173`），登录自己刚创建的账号。Vite 将 API 转发到本机 3000。使用完成后 Ctrl+C 停止，并在该终端执行 `Remove-Item Env:NODE_ENV`。

**当前监听边界：** Vite 绑定 `127.0.0.1`；`server/index.js` 的 API 绑定 `0.0.0.0:3000`。不要给 API/数据库放行公网或局域网入站权限。项目有记录在案的原生模式监听收口待办，不能以旧文档的“仅监听本机”代替实际检查。

若只需完整容器预览，可以在另一份独立克隆目录双击 `启动网站.bat`，由脚本选择 Docker 模式并完成本地配置；不要把原生 `.env` 原样拿给 Compose，里面的数据库主机不同。同机多个 Compose 项目必须使用不同项目名、端口和卷。停止容器时不使用 `down -v`，以免删除本地数据。

## 4. 日常开发、更新和审核

每项工作先建立一个 Issue，使用“协作任务”模板，指定一位负责人、目标和验收条件。一个任务对应一条 `codex/*` 分支；同一任务的 AI 会话都引用该 Issue 和分支。

工作区干净时开始新任务：

```powershell
git status --short
git switch main
git pull --ff-only origin main
git switch -c codex/123-short-description
```

`123-short-description` 替换为实际任务编号和简述。有未提交修改时，先由原任务负责人保留到对应分支，不能用 `reset --hard` 或目录覆盖来清理。多人同机工作时使用独立克隆或独立 worktree；每个运行中的开发实例另行处理端口和数据库，worktree 不自动隔离数据库。

开发前读取 `AGENTS.md`、`.ai/README.md`、`.ai/router.md`，执行 `npm run ai:context -- <实际目标路径>`。改动完成后同步涉及的系统文档；路由、权限、迁移、环境变量或测试入口变化时先执行 `npm run ai:docs:build`。

提交前执行 `npm run check`、`npm run audit:prod`、`git diff --check`，并按变更范围完成浏览器验收。只暂存自己任务涉及的文件，查看 `git diff --cached` 后提交。推送与提交 Draft PR：

```powershell
git push -u origin HEAD
gh pr create --draft
```

PR 正文使用仓库模板，填写实际结果和未验证项。开发完成后转为 Ready，请另一位维护者审阅。AI 可以辅助找问题，批准由另一维护者使用自己的身份完成；作者不能换用他人账号批准自己的 PR。

合并前如果 `main` 有更新，在干净的任务分支执行：

```powershell
git fetch origin
git merge origin/main
git push
```

冲突按业务语义解决，不整份选择“我的”或“对方的”；已有线上迁移不能改写。两人新增相同迁移编号时，未发布的一方调整编号并重验。生成事实冲突通过生成器重建，`.ai/sessions.md` 合并后只留最近五条。合并更新后重新检查，等待最新提交的 CI 通过。

合并 PR 后，在干净工作区切回 `main` 并执行 `git pull --ff-only origin main`。依赖锁文件变化时执行 `npm ci`，本地应用重启会执行未应用迁移。合并完成不等于正式上线。

### 两阶段 GitHub 门禁

| 阶段 | 配置 | 进入条件 |
| --- | --- | --- |
| 单维护者接入准备 | 强制 PR、两项 required checks、分支保持最新、解决全部讨论；管理员受限、禁止强推和删除；暂不要求他人批准 | 第二位维护者尚未接受邀请 |
| 双维护者日常协作 | 在上述规则上增加至少一位其他维护者批准、推送新修改使旧批准失效、关键路径负责人审核 | 第二位维护者已接受邀请且具备审核资格；已将其加入关键路径 CODEOWNERS |

管理员在 Settings → Branches → `main` 的现有规则中配置，保留两项 required checks 和管理员限制；不要新建一条相互竞争的分支规则。第二阶段先更新 `CODEOWNERS`，再启用负责人审核，否则只登记一个负责人时，该负责人自己的 PR 会缺少合格审核者。

第二阶段的设置项为 Require a pull request before merging、1 approval、Dismiss stale pull request approvals、Require review from Code Owners、Require conversation resolution。当前实际启用情况见 [实施计划](协作工作流实施计划.md)，不可只凭本表假定配置已生效。

## 5. AI 会话与任务交接

每个人使用自己的 Codex 账号和本机配置。仓库内的规则随 Git 同步；个人记忆、个人插件、终端历史和聊天记录不会因此成为对方已知的项目事实。无需同步 `.codex` 用户目录，也不要求两人使用相同模型。

新成员可以直接给自己的 AI 发送：

```text
这是风起游戏管理后台仓库。先读 AGENTS.md、.ai/README.md、.ai/router.md 和
docs/协作开发与交接.md，检查分支及未提交修改。
当前任务：填写 Issue 链接；目标分支：填写分支名。
对涉及的文件执行 npm run ai:context，再按任务验收条件工作。
保留其他人的修改，只提交本任务文件，完成适用检查和 PR。
不要绕过他人审核；正式发布必须核对本次指定发布人和独立云身份。
未完成时按 PR 模板填写交接，注明最新提交、未验证项和下一步。
```

交接未完成任务时，原负责人先保存到远程分支并更新 Draft PR。接手人用 `gh pr checkout <编号>` 获取代码，在新的 AI 会话中给出 PR 链接和交接摘要。任何尚未提交的修改都不会因提供 PR 链接而传递。

| 信息 | 保存位置 |
| --- | --- |
| 当前任务进度、待办、最新 SHA、下一步 | Issue / PR 模板 |
| 当前业务规则与不变量 | `.ai/systems/` |
| 长期架构取舍 | `.ai/decisions/` |
| 最近重要任务摘要 | `.ai/sessions.md`，最多五条 |
| 发布版本、备份、恢复与验收 | `docs/部署与运维.md` 及发布记录 |

AI 会话分享只作为补充；共享快照不自动随新消息更新，也不授予项目访问权。分享前检查受众及内容，个人账号链接可能对持有链接的人开放。官方页面描述的入口有平台范围，另一台机器以实际可用功能为准。[OpenAI 说明](https://learn.chatgpt.com/docs/use-chatgpt#share-a-read-only-snapshot-of-a-codex-thread)

## 6. 正式发布与独立授权

正式发布由本次指定且已完成云身份配置的维护者执行。当前第二位维护者 `axbca` 已获项目负责人发布授权，其独立 RAM 用户为 `fq-deployer-axbca`；具体登录和应用分配进度见实施计划。后续新增人员仍需明确授权，不能因为接受 GitHub 邀请就推断已有云权限。

管理员为对方创建或选定独立 RAM 用户，启用适用的 MFA、登录策略，授予 [既有云助手策略](../运维/阿里云云助手最小权限策略.json)，并在 RAM → OAuth 应用 → `official-cli` 中分配该身份。不要复制原发布人的 CLI 配置，也不需要把 RAM 管理权限授给发布人。该策略含 `ecs:RunCommand`，能在正式实例执行命令；它限制目标实例和云 API 范围，但不限制命令只能发布，也不阻止命令访问实例上的数据。

对方安装支持 OAuth 的阿里云 CLI，在自己的设备运行：

```powershell
aliyun configure --profile fq-production --mode OAuth
aliyun sts get-caller-identity --profile fq-production
```

浏览器使用获准的个人 RAM 身份，选择中国站和 `cn-guangzhou`；管理员需要预先完成 `official-cli` 分配。`GetCallerIdentity` 返回的身份应属于本人 RAM 用户，不能只看到配置名就认为身份正确。身份核验结果只在本地核对，凭据不贴入 Issue 或聊天。[阿里云 OAuth 文档](https://help.aliyun.com/zh/cli/oauth-credentials)

仓库云助手脚本默认 CLI 路径是 `$env:LOCALAPPDATA\AliyunCLI\aliyun.exe`。安装在其他目录时，每次调用通过 `-AliyunCliPath (Get-Command aliyun).Source` 指定自己的实际路径，不修改公共脚本来迁就个人路径。

发布只使用 [publish-fq-admin](../.agents/skills/publish-fq-admin/SKILL.md) 和 [部署与运维](部署与运维.md)。先建立“正式发布记录”Issue，填目标完整 SHA、发布人及回滚基线。只有已进入 `main` 且该提交 CI 成功的版本可发布；同一时刻一个发布人执行一次发布，备用发布人接管前确认旧任务和远端执行均已结束。

既有顺序为双备份及 OSS 校验 → 制品校验 → app-only 切换 → 健康与业务验收 → 保留回滚证据。远程写入阶段按发布技能持有同一互斥锁，备份至失败回滚结束期间不可拆成相互无锁的多个云助手任务。只改文档、模板和技能时不重新部署应用。

发现云助手本地超时或断线时，先查询原 invocation 的远端状态；不能立即重复投递。数据库迁移只追加；存在旧应用不兼容的新结构时，先解决兼容性，不能承诺切旧镜像即可恢复。数据库恢复属于单独危险操作，不自动随镜像回滚执行。

正式版本以服务器 `.release-commit` 和镜像 revision 为准，GitHub `main`、文档归档提交和线上版本允许不同。发布记录保留实际目标、版本、制品摘要、备份编号、回滚基线、验收与未验证项；公开记录不得附生产数据或备份文件。

## 7. 第一次共同维护的验收

- 对方用自己的账号成功接受邀请、克隆，并推送自己的任务分支。
- 在对方电脑通过 `npm run check` 和依赖审计；本地数据库和管理员由对方自行创建，完成登录。
- 对方提交一个真实的小范围 PR，另一维护者审阅，最新提交两项 CI 通过后合并。
- 在接手人的新 AI 会话中，单凭仓库、Issue / PR 和最新 SHA 能继续任务。
- 管理员完成第二阶段门禁，核对双方关键路径审核资格；不给 AI 设置绕过规则。
- 获准发布的人核对自己的云身份，在一次需要上线的真实变更中完成发布、验收和记录；单独在隔离环境做恢复演练，不为了接入验收回滚正式数据库。
- 离开项目时撤销 GitHub 写权限、RAM 策略及 OAuth 应用分配、适用的后台账号和应急 SSH 授权；不因离职而删除代码历史或业务数据。

GitHub 协作邀请参考：[官方说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/inviting-collaborators-to-a-personal-repository)。
