# 协作工作流实施计划

日期：2026-09-07。适用仓库：`jiutubaba/FengQiGame`。成员接入操作见 [协作开发与交接](协作开发与交接.md)。

## 目标与职责

- 每项工作有负责人、可审查的 PR、明确的验证结果和下一步。
- 每位维护者使用独立 GitHub、Codex 和必要的云身份。
- `main` 表示已合并代码；服务器 revision 表示实际发布版本。
- 项目负责人确定成员和权限、发布职责及紧急接管；任务负责人负责代码与文档；另一维护者审核；指定发布人负责双备份、发布、验收及回滚证据。
- 当前采用现有个人公开仓库，不在接入阶段迁移归属、改变可见性或开通新服务器。

## 实施顺序与验收

| 阶段 | 工作 | 负责人 | 完成条件 |
| --- | --- | --- | --- |
| 1：仓库准备 | 接入手册、Issue / PR 模板、关键路径 CODEOWNERS、AI 交接和权限边界、发布互斥规范 | 当前维护者 / AI | 文档检查、单元测试、构建、依赖审计、PR CI 通过并合并 |
| 1：远端门禁 | 保留原有两项 CI、strict、管理员约束、禁止强推和删除；补充强制 PR 与讨论解决 | 仓库管理员 | GitHub API 回读生效配置；此时批准人数暂为 0 |
| 2：成员接入 | 确认用户名、邀请接受、独立登录、本地初始化、首个任务 PR | 项目负责人 / 第二位维护者 | 对方电脑登录本地服务、推送分支、CI 成功 |
| 2：交叉审核 | 将第二位维护者加入关键路径 CODEOWNERS，启用 1 位批准、旧批准失效和负责人审核 | 仓库管理员 | 两位维护者均能审核对方 PR；作者不能自行满足批准要求 |
| 3：发布接管 | 确认发布授权、独立 RAM 与 OAuth 分配、指定发布人、远端互斥、实际业务验收 | 项目负责人 / 发布人 | 发布记录关联目标 SHA、备份、镜像、回滚基线和实测结果 |
| 4：自动发布 | 统一 Actions 发布入口、受控 production 环境、固定 SHA / 制品摘要、受限自动化身份和并发控制 | 维护者共同评审后实施 | 受控身份实际认证成功，重复发布被阻止，失败可回滚，审计与恢复演练通过 |

## 自动发布的实施约束

1. 先选定执行环境和身份方案，验证阿里云支持的短期角色凭据链；不为赶进度复制个人 OAuth 文件或引入长期主账号密钥。
2. 只接收已合并且 CI 通过的完整 SHA；构建一次，以制品摘要固定发布内容。人工选择发布时机，合并不自动等于上线。
3. 建立 `production` 环境及发布权限，部署工作流、回滚入口共用同一并发组，`cancel-in-progress: false`；服务器侧继续互斥，涵盖人工云助手入口。
4. 普通 PR CI 不访问生产凭据或生产网络，不把拥有生产身份的执行器提供给任意 PR 代码。
5. 自动化覆盖双备份 / OSS 校验、app-only 切换、迁移兼容性检查、健康和资源校验、失败回滚及版本记录；登录态页面和真实游戏联调仍按变更风险验收。
6. 先在隔离环境验证失败和恢复，再用于正式变更。启用后的代码、技能、文档、云身份和 GitHub 设置一起验收。

GitHub 支持部署环境、保护规则和并发控制，具体功能随仓库可见性及套餐核对：[官方部署文档](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments)。
