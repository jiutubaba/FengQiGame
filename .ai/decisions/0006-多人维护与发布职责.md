# ADR-0006：多人维护与发布职责

- 状态：已接受
- 日期：2026-09-07

## 背景

项目开始由多位维护者共同开发和发布。现有 CI、AI 文档及发布流程可复用，但个人身份、未提交代码和本地会话不能成为团队共同工作的隐含前提。

## 决策

- 每人使用独立身份和工作副本；Issue 确定负责人，任务分支通过 PR 和 CI 合并。
- 第二位维护者接受邀请前采用强制 PR、CI 与讨论解决的准备阶段；接受邀请并登记负责人后启用至少一位其他维护者批准和关键路径负责人审核。
- AI 的项目长期授权不授予他人的身份，也不能绕过 GitHub 审核或云权限；每次正式发布指定发布人，同一时刻一项发布，服务器写入阶段持有统一锁。
- 稳定知识进入现有 `.ai/`，任务交接进入 Issue / PR；个人 AI 会话与认证配置不进入 Git。
- 正式版本按运行时 revision 和镜像识别，合并与发布分别记录。纯文档及技能改动不重复部署应用。
- 初期保留本机独立 OAuth 与云助手入口，自动化发布另行验证受控身份和恢复能力后启用。

## 后果

- 第二位维护者能从仓库和 PR 接续工作，生产授权可以独立撤销。
- 强制交叉审核依赖另一位合格维护者在线；不以临时降级门禁作为日常处理方式。
- 云助手命令权限属于服务器运维能力，不能描述为受限的单一发布按钮；发布规范与技术权限需分别核验。

## 验证

按 [协作工作流实施计划](../../docs/协作工作流实施计划.md) 完成 GitHub 设置回读、新成员首次 PR、新 AI 会话接手和独立发布验收；只记录实际完成的阶段。
